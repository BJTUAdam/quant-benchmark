# 多窗口相对强弱分歧下的排名裁决、换仓队列与部分执行维护

> 题目规格包：程序校验与本轮模型交叉审阅已完成；外部API复核未执行，未写入自动接纳库。数据待绑定，运行待接入。

研究目标：在同一股票池的不同回看尺度给出相互冲突的强弱排名时，如何裁决入选和留存，并把受成交容量、涨跌停、T+1及成本预算限制的换仓意图维护为可撤销且不重复下单的队列？研究必须区分信号目标、待执行指令和实际持仓，而非每次计算排名后立即假设全部换仓完成。

## 运行协议

先在研发期开发首版，再经历七段逐步揭晓的正式期。每段运行时冻结代码；完成后可以保持、调参或修改逻辑。
现金、持仓、未完成订单和JSON memory连续。修改不重置账户，不覆盖过去结果。全部七段的连续账户用于评价。
实际虚拟时间范围、数据版本和分段边界在绑定后确定。

## 研究决策

- 使用已完成日线与当时可见复权因子定义至少两种回看尺度的可比强弱特征，记录窗口、有效样本、方向和特征版本。；相互影响：特征本身及其版本先冻结到当日信号快照，再交给rank_aggregation；不能因尚未成交而重写过去得分。
- 研究多窗口排名一致、冲突与样本不足三种输入如何得到可比较的候选优先级，以及并列和缺失值的处理。；相互影响：输出除排序外还需保留冲突程度，供holding_buffer决定是否值得改变目标；不直接把冲突程度规定为最佳买卖信号。
- 分别定义新进入与继续持有条件，并研究排名反转时保留、替换或撤销尚未执行的目标。；相互影响：只产生目标变更请求；turnover_budget据其优先级安排执行，已持有状态与待买状态不得混成同一个排名缓冲判断。
- 依据当前已知成交额和逐日可交易规则估计可参与容量；对无法卖出或买入的标的保留原因。；相互影响：容量约束由turnover_budget用于估计每次队列可实现部分；不将缺行情、涨跌停或T+1限制统一当作信号失效。
- 将成本和单次换仓约束映射为带时效的卖出/买入队列，研究旧指令过期、信号翻转、部分执行和撤单先后次序。；相互影响：接收holding_buffer目标及liquidity_filter容量；先保留需卖资金与已挂指令占用，再给capital_allocation可用额度，下一时点由state_migration恢复队列。
- 在目标名单、可用现金、未成交委托占用和不可卖库存之间分配权重与整手数量，研究无法立即完成的目标如何分期实现。；相互影响：只发送本次准许的订单，实际成交反馈写入state_migration；计划卖出资金不能提前当作可用现金。
- 用JSON保存目标版本、指令ID、创建时点、剩余数量、过期依据和最后确认的实际持仓；更新参数或逻辑时重建仍有效的队列。；相互影响：每一时点先核对账户和旧委托，再交给turnover_budget处理新目标；修改不能重复发送已成交部分，不能删除未实现风险。

可研究的参数与结构选择：

- 参与比较的回看尺度集合及最小有效样本
- 收益、波动或相对基准强弱的可比口径
- 多窗口得分合成、冲突表达和并列处理
- 新入选门槛、继续持有门槛及冲突状态缓冲
- 队列排序依据和风险卖出与新增买入的优先级
- 每次及滚动换仓预算与费用估计
- 候选成交容量及订单分拆方式
- 待执行指令的有效期与失效触发
- 信号翻转时保留、缩减、撤销和替换的规则
- 单票权重、现金留存及整手余量处理
- 部分成交后的剩余目标计算
- 参数版本更新时旧队列的迁移和去重键

持续维护依据：后续阶段可能从多尺度一致变为持续分歧，也可能出现强者难买、弱者难卖或撤单重发频繁。维护需要判断调整排名裁决、留存缓冲还是队列时效；三者会改变实际换手与现金占用。每次维护都延续同一账户、挂单和JSON memory，并对比目标与实际持仓差距。尚无轨迹证明该任务具有确定长程难度或收益优势。
